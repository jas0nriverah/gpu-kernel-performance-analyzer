All model selection was frozen before this additional device was requested. New-device captures are evaluation evidence, not training or hyperparameter-selection data.

The default preflight accepts the explicit unsupported MIG marker `[N/A]` on full GPUs while rejecting enabled/unknown states, multiple device visibility, conflicting allocations, and active compute processes. It verifies runtime ordinal zero against the selected UUID's PCI bus address. `CUDA_VISIBLE_DEVICES` is normalized to that exact allocated UUID.

Spark reports unsupported `nvidia-smi` framebuffer memory totals/usage, memory clocks, MIG mode, and power limit. These values are preserved as unavailable. Missing memory-clock telemetry remains null/empty in raw capture and is never replaced with zero. [NVIDIA's known-issues documentation](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html) explains that integrated GPUs share system DRAM rather than dedicated framebuffer memory. Preflight separately records `cudaMemGetInfo` capacity with that API as its source; it is runtime-visible shared/device memory, not an NVML framebuffer measurement, and may omit memory that could be reclaimed by the host.

The `power.draw` sensor is available. [NVIDIA's official Spark power clarification](https://forums.developer.nvidia.com/t/dgx-spark-power-clarification/349668) states that `nvidia-smi` wattage measures the GPU. Existing capture manifests retain the schema label `power_scope=gpu_board`; for this integrated GB10 device, interpret that label as **GPU-only sensor power**, excluding CPU and total SoC/system power. Neither a power-limit value nor system energy is inferred from unsupported metrics.
